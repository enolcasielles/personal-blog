## Introduction

In this article I want to share my experience developing **Fluento**, a mobile application that seeks to offer an efficient and fun way to improve your English. It is an educational project that seeks to explore how to use different technologies to create a useful and scalable application.

## What is Fluento?

Fluento is a mobile application that offers a solution to improve your English using the reverse translation methodology. The user receives a sentence in Spanish and must translate it into English. This methodology, widely used by renowned academies, has demonstrated very satisfactory results. Repetitive practice improves vocabulary, fluency in sentence construction, and confidence in expressing oneself in English.

### Main Features

1. **Real-time reverse translation**: The user hears a sentence in Spanish and must say it in English.
2. **Intelligent adaptation**: Using an algorithm inspired by Anki, Fluento learns from mistakes and makes you practice more those structures that are more difficult.
3. **AI-powered list generation**: The application content is automatically generated by AI.
4. **AI-powered evaluation**: Responses are evaluated by AI models that focus on grammar and vocabulary.

### How it Works

The system is based on phrase lists, where each list contains units composed of a sentence in Spanish and its translation into English. Lists have parameters such as difficulty level, theme, and grammatical structures.

There are two types of lists:
- **Public**: Managed by the platform and accessible to any registered user.
- **Private**: Created by Premium users and accessible only to them.

### Freemium Model

The application implements a freemium model with the following features:
- **Free Plan**: Limited access to the platform with a restricted number of daily phrases.
- **Premium Plan**: Unlimited access and ability to create personalized lists.

## Main Functionalities

### Practice System

The heart of Fluento is its reverse translation practice system, which works as follows:

1. **Intelligent Selection**: The system chooses phrases based on your level and previous performance, ensuring progressive and personalized learning.

2. **Exercise Flow**:
   - You listen to and read the sentence in Spanish
   - You have a few seconds to translate it into English
   - You say it out loud
   - The system evaluates your response and shows you the correct answer along with a score

3. **AI Evaluation**: 
   - Your spoken response is converted to text using speech recognition technology
   - An AI model evaluates grammatical accuracy and correct vocabulary usage
   - You receive a score based on your response
   - The system calculates the best next phrase and you start the cycle again

### List System

Lists are the way we organize learning content:

1. **Public Lists**:
   - Created and curated by the Fluento team
   - Organized by difficulty levels and themes
   - Regularly updated with new content
   - Accessible to all users

2. **Personalized Lists** (Premium):
   - Creation of your own lists
   - Customization of parameters such as:
     - Difficulty level
     - Specific theme
     - Grammatical structures to practice

### Adaptation System

Fluento learns from your interaction to optimize your learning experience:

   - Inspired by the Anki methodology
   - Phrases that are more difficult for you appear more frequently
   - Phrases you master are less likely to appear

## Architecture and Technologies

The platform consists of several key elements:

### 1. Mobile Application (React Native + Expo)

Developed with React Native to cover both iOS and Android with a single code base. We use Expo for its mature ecosystem, impeccable development experience, and wide variety of libraries.

### 2. Backend (NestJS)

For the backend we chose NestJS for its multiple advantages:
- Robust and mature framework for Node.js
- Modular and scalable architecture inspired by Angular
- Excellent support for TypeScript and decorators
- Integrated dependency injection system
- Wide variety of official modules for common functionalities

### 3. Database (PostgreSQL + Prisma)

We use PostgreSQL through Supabase, with Prisma as ORM. This combination offers us:
- Robust and scalable database
- Type-safe TypeScript system
- Flexibility for future migrations. Using Prisma instead of the Supabase API allows us to switch to another database system if needed.

### 4. Authentication (Supabase)

Supabase provides us with a robust authentication system with support for multiple OAuth providers. For now, we will only use an email/password authentication system. But the system is prepared to support more authentication providers in the future.

### 5. Corporate Website (NextJS)

A simple website developed with NextJS that serves as an entry point for new users:
- Explanatory landing page of the product
- Help and documentation section (pending)
- Necessary legal pages (pending)
- Possibility to easily create pages for marketing campaigns

### 6. Asynchronous Processing (Kafka + Process Worker)

To handle heavy tasks and background processing, we implement:

- **Apache Kafka**: As a messaging system to manage events and asynchronous tasks
- **Process Worker**: An independent TypeScript application that:
  - Consumes Kafka events
  - Processes background tasks, such as list generation

This architecture allows us to:
- Horizontally scale task processing
- Efficiently handle load spikes
- Separate processing logic from the main API
- Deploy the API in a serverless environment and processing in a continuous execution environment.

## Involved Projects

For the platform development, I chose to separate the different components into 2 independent projects.

- **fluento-monorepo**: For the rest of the elements, a monorepo was defined with `pnpm` in which different applications and packages coexist that support the API, Process Worker and Corporate Website. You can see the code [here](https://github.com/enolcasielles/fluento-back).

In the following sections, we will see the main characteristics of each of these projects. I will not go into detail in explaining in depth the implementation carried out to avoid making the article too long. I will only explain the most relevant features.

## Monorepo

The `fluento-monorepo` project is structured into two main directories: `apps` and `packages`. This organization allows us to maintain modular and reusable code, where packages provide common functionality that can be used by different applications. If you want to better understand how this type of structure works, I recommend [this article](https://enolcasielles.com/blog/monorepo) where I explain how it works and how to create a monorepo with pnpm.


### Packages (`packages`)

In the `packages` directory we find the shared code that supports all applications:

The `core` package encapsulates all common business logic between different applications. Here we define shared types and interfaces, implement utilities and helpers that are used in multiple places, and maintain the global constants and configurations that the entire platform needs.

The `database` package centralizes everything related to data persistence. It contains the Prisma schema that defines our data structure, migrations that keep the database updated, models and types that represent our entities, and is where we would define any other functionality that helps us facilitate data access from any application.

The `kafka` package is simple but effective. It contains a single file that implements key components for applications to efficiently manage any related aspect. On one hand, it exposes the `produceMessage` method so applications can send messages to a Kafka topic. On the other hand, it exposes an abstract `KafkaConsumer` class that facilitates the implementation of consumers easily and efficiently. Additionally, TypeScript generics are used to allow applications to define the type of data sent and received. Finally, it exposes the `initKafka` method that allows creating Kafka topics to be used on the platform.

### Applications (`apps`)

On the other hand, the `apps` directory contains the different applications that make up Fluento's backend and web:

The `api` application, developed with NestJS, constitutes the backend's core. It is responsible for managing all mobile application requests and implements the main business logic. Additionally, it handles all user authentication and authorization. The architecture has been designed with deployment in a serverless environment in mind, which will allow us to optimize costs and scale according to demand.

The `process-worker` application, developed with TypeScript, is an independent application designed to handle asynchronous processing. Its main responsibility is to consume Kafka messages and execute computationally intensive or long-duration tasks, which should not be executed in the same thread as the API. For now, only phrase list generation is included. But it is perfectly prepared to add new tasks in the future. The procedure is simple. Just create a new `consumer` as a class that inherits from `KafkaConsumer` and implements the `onMessage` method with the logic of the new task.

The `web` application contains the corporate website, built with Next.js, serves as the main entry point for new users, marketing actions, etc. It includes an attractive landing page that presents the product and, in the future, a complete documentation portal, a technical blog where we share our experiences and learnings, and all the legal pages necessary for service operation.

Finally, the `infra` application contains all the configuration necessary to set up the local development environment. This includes a PostgreSQL database, a Kafka server, and a web interface to manage the Kafka cluster.

This modular structure provides numerous benefits to our development. By centralizing common code in shared packages, we eliminate duplication and ensure consistency throughout the platform. The clear separation of responsibilities facilitates maintenance and would allow different teams to work in parallel on different applications. Additionally, each application can be deployed independently, giving us great flexibility in managing releases and updates.

### Why is the Process Worker not implemented in the NestJS application?

I want to emphasize this aspect which can be a bit confusing. The NestJS application has been designed to be deployed in a serverless environment, which allows us to optimize costs and scale according to demand. By definition, in a serverless environment there is no machine in continuous execution, but it is activated on demand when a request comes in.

However, for processing Kafka events, code in continuous execution is needed. Every time a new event enters the queue, the consumer must receive and process it. Therefore, a serverless environment **is not suitable**.

That's why the API and Process Worker are separated into independent applications. The API is deployed in a serverless environment and the Process Worker is deployed in a continuous execution environment. The API, when necessary (such as when generating a new list), uses the `produceMessage` method from the `kafka` package to send a message to the topic. On the other side, the Process Worker application, which has the Consumer continuously listening, is responsible for receiving that message and processing it.

## System Algorithms. Generative AI.

A key aspect of Fluento is the use of AI models for different tasks. All this implementation has been done using the OpenAI API and using different models it offers us. This implementation has been carried out in the `core` package, in the `engine` directory. Let's see the different functionalities implemented:

### List Generation

The `list-generator.ts` module implements automatic phrase list generation. Using `gpt-4o-mini`, a list of phrases in Spanish is generated along with their English translation. For this, it takes into account the following parameters:
- The desired difficulty level
- The specific theme of the list
- The grammatical structures to be practiced
- The number of phrases to generate

Additionally, it is asked to generate a brief description of the list, between 10 and 20 words, that summarizes the list's content. Finally, it is specified to give a response in JSON with the desired schema.

### Answer Evaluation

In `evaluate-answer.ts` we find the logic to evaluate user responses. Using `gpt-4o-mini`, the user's response is analyzed by comparing it with the correct translation. The evaluation is comprehensive and considers:

1 = Incorrect (very different meaning or incomprehensible response)
2 = Partially correct (has errors but maintains part of the meaning)
3 = Correct (same meaning, small variations may exist)

It is asked to return only the evaluation number (1, 2, 3).

### Audio to Text Conversion

The `audio-to-text.ts` module uses OpenAI's Whisper model to transcribe user audio to text. This module will be used to convert the user's spoken response to text that will allow us to evaluate it with the previous module.

### Text to Audio Conversion

In `text-to-audio.ts` we implement audio generation from text using OpenAI's TTS (Text-to-Speech) model. This component allows us to convert questions and answers that the user must hear in the application to audio.

**Note**: The previous 2 modules have finally not been used in the application. After tests and evaluations, we have opted to use native libraries that allow us to perform this conversion from the mobile application itself, avoiding OpenAI costs and improving latency. On the other hand, the result is not as good as that obtained using OpenAI's TTS model. In any case, we keep these modules in case they want to be used again in the future.

### Image Generation

The `generate-list-image.ts` module implements an interesting process to generate representative images for each phrase list, combining OpenAI's generative AI with the Unsplash image service:

First, it uses `gpt-4o-mini` to generate creative search terms based on the list's theme. For example, if the list is about "Travel", the model could generate terms like "adventure journey", "scenic landscapes", "cultural exploration", etc.

Finally, these search terms are used to get a random image from Unsplash, adding "General English" as a fallback term to guarantee results (in case the other terms don't produce results).

This hybrid approach provides us with several advantages:
- High-quality, royalty-free images from Unsplash
- Creative and contextual search terms thanks to AI
- Greater variety of results by combining multiple search terms

### Response Time Calculation

Although this part is not an AI algorithm, the `calculate-response-time.ts` module implements an algorithm that, based on the phrase's difficulty and the length of the response the user must give, calculates the time we will give the user to respond. The application will use this calculated time to allow the user to give their response.

### Spaced Repetition Algorithm

Finally, the `generate-next-unit.ts` module implements the algorithm that decides which phrase the user should practice at each moment. This algorithm, based on the Anki system, is fundamental for optimizing learning, as it ensures the user practices more those phrases they need to reinforce and less those they already master.

The algorithm calculates a score for each phrase based on four main factors:

1. **Historical Performance (40% of final weight)**
   - The average of scores obtained in previous practices is calculated
   - The worse the performance on a phrase, the more likely it is to appear
   - Never-practiced phrases have initial priority

2. **Time Since Last Practice (30%)**
   - It considers how much time has passed since the last time it was practiced
   - Phrases that have gone longer without practice are more likely to appear
   - It is normalized with respect to the maximum time without practice in the phrase set

3. **Practice Frequency (20%)**
   - It takes into account how many times each phrase has been practiced
   - Less practiced phrases are more likely to appear
   - Helps maintain balance in the practice of all phrases

4. **Random Factor (10%)**
   - Adds an element of randomness to the algorithm
   - Avoids predictable patterns in selection
   - Ensures variety in practice

The final score of each phrase is calculated using the formula:

```typescript
finalScore = 0.4 * (1/performance) + 
             0.3 * (timeWithoutPractice/maxTime) + 
             0.2 * (1/(timesPracticed + 1)) + 
             0.1 * random()
```

This algorithm ensures that:
- Phrases with worse performance are practiced more frequently
- No phrase is forgotten for too long
- The user maintains balanced progress on all phrases
- Practice is varied and not predictable
